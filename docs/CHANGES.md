# Server Manager 2.0 — что изменено, что найдено, что проверено

Документ написан по результатам аудита версии 1.5.0 и доработки. Числа в разделах «Скорость» и «Тесты» получены в конкретной среде (см. оговорки).

## 1. Результаты аудита версии 1.5.0

### Почему загрузка и скачивание были медленными и ненадёжными

| № | Находка | Последствие |
|---|---|---|
| 1 | Загрузка шла одним запросом через `multer` во временную папку `.uploads`, а потом файл копировался на место | двойная запись; при другом диске — см. п. 2 |
| 2 | Если назначение на другом диске, файл переносился **синхронным** `fs.copyFileSync` | вся панель (все запросы, консоли, WebSocket) «замирала» на время копирования; на 1 ГБ — 2,3 с, на сотни ГБ — десятки минут |
| 3 | У `multer` стоял лимит `maxUploadMb` (по умолчанию 512 МБ) | файл больше 512 МБ нельзя загрузить |
| 4 | Таймауты Node.js по умолчанию: `requestTimeout` = 5 минут | любая загрузка дольше 5 минут обрывалась; настроек не было |
| 5 | Нет докачки: при обрыве всё начиналось заново; нет отмены и очереди | на больших файлах загрузка практически невозможна |
| 6 | Прокси на удалённые серверы открывал новое TCP-соединение на каждый запрос | лишние задержки (особенно для множества небольших запросов) |
| 7 | Список папки: синхронный `statSync` для каждого файла, без постраничной выдачи | подвисание панели и браузера на больших папках |
| 8 | Копирование файлов потоком с буфером 64 КБ, без отмены | медленнее и без управления |
| 9 | Скачивание папок: сжатие ZIP уровня 5 «на лету» | процессор — узкое место; игровые файлы почти не сжимаются |
| 10 | Токен входа передавался в адресе скачивания (`?token=…`) | токен попадает в историю браузера и журналы прокси |

### Безопасность и права

| № | Находка | Серьёзность |
|---|---|---|
| 1 | Права проверялись списком регулярных выражений на «роль»; роли только скрывали кнопки; индивидуальных прав не было | основа доработки (раздел 8 ТЗ) |
| 2 | На удалённом сервере параметр `disk` в **теле** запроса не проверялся панелью, а агент считал любой запрос от панели администраторским: оператор, судя по коду, мог работать с любым диском удалённого компьютера (на старой версии не воспроизводилось) | высокая |
| 3 | Если администратора переименовывали, при старте заново создавалась учётная запись `admin` / `admin` | высокая |
| 4 | Смена пароля не отзывала выданные токены | средняя |
| 5 | Подбор пароля ограничивался только по IP | средняя |
| 6 | В Docker имя образа и контейнера из запроса попадали в командную строку без проверки (можно подставить параметр вроде `--privileged`) | высокая (для имеющих доступ к разделу) |
| 7 | В консоль приложений по WebSocket приходил вывод всем вошедшим | средняя |
| 8 | Нет защитных заголовков браузера (CSP, X-Frame-Options, nosniff) | низкая |
| 9 | Запись в журнал не велась для файловых операций (удаление, переименование, загрузка) | низкая |

## 2. Что сделано

**Передача файлов (разделы 1–3 ТЗ)**
- Загрузка частями с докачкой (`lib/transfers/uploads.js`): сессии на диске, проверка смещения, откат недописанной части, временный файл рядом с местом назначения (переименование мгновенное), проверка свободного места до начала, замена существующего файла только после полной загрузки, отмена и автоочистка брошенных загрузок (48 часов).
- Лимит файла 500 ГБ (`limits.maxFileGb`), таймауты вынесены в `config.json` и разделены: время получения запроса, неактивность соединения, «зависание» загрузки, ожидание удалённого сервера. Бесконечных таймаутов нет.
- Скачивание потоком с `Range`, `If-Range`, `ETag`, обратным давлением (`lib/transfers/download.js`); папки и наборы файлов — ZIP без сжатия.
- Одноразовые «билеты» на скачивание вместо токена в адресе.
- Очередь передач в интерфейсе: скорость, объём, остаток времени, пауза/продолжение/отмена, автоповторы, продолжение после перезагрузки страницы, загрузка папок перетаскиванием.
- Копирование и перемещение — потоком, 4 МБ буфер, прогресс, отмена, проверка перед удалением оригинала, пакетные операции.
- Постоянные соединения (keep-alive) панели с удалёнными серверами.

**Файловый менеджер (раздел 4 ТЗ)** — список/плитки, хлебные крошки, выделение, пакетные операции, контекстное меню, поиск, сортировка на сервере, постраничная выдача, перетаскивание, горячие клавиши, редактор, распаковка.

**«Использовать проект» (раздел 5 ТЗ)** — `lib/projects.js` + `public/js/project-dialog.js`.

**Навигация (раздел 6 ТЗ)** — адреса `#/…`, штатная история браузера, восстановление папки и прокрутки.

**Рефакторинг (раздел 7 ТЗ)** — `server.js` (738 плотных строк) разделён на модули `lib/…`; обработчики получили понятные имена параметров (`req, res`, `appRecord`); весь «перенесённый» код автоматически развёрнут из однострочного вида; добавлены комментарии на русском; убраны неиспользуемые зависимости (`multer`, `mime-types`) и устаревшие скрипты-установщики (`apply-remote.js`, `install-m9.js`); клиентский `app.js` разделён на модули; написан `README.md`.

**Права (раздел 8 ТЗ)** — 33 разрешения в 8 группах, три готовые роли, индивидуальные «добавить/убрать», зависимости между правами, таблица «маршрут → право» с запретом по умолчанию, двойная проверка на удалённых серверах, защита от повышения привилегий, доступ к серверам.

**Безопасность (раздел 10 ТЗ)** — см. список находок выше; всё перечисленное исправлено.

## 3. Исправленные ошибки

Ошибки версии 1.5.0 (найдены чтением кода; запуск старой версии для их воспроизведения не выполнялся, кроме измерения блокировки из раздела 4):

- Синхронное копирование блокировало панель.
- Загрузка больше 512 МБ или дольше 5 минут не работала.
- Обход проверки прав через `disk` в теле запроса на удалённых серверах (по анализу кода).
- Воскрешение `admin` / `admin` при переименованном администраторе.
- Старые токены после смены пароля.
- Подбор пароля только с ограничением по IP.
- Инъекция параметров в Docker.
- Вывод консоли приходил всем пользователям независимо от прав.

Дефекты новых модулей, найденные тестами во время разработки (в релиз не попали, перечислены для прозрачности):

- в «Файлах» первый клик по строке сдвигал список (появлялась панель выделения), и двойной клик не открывал папку — найдено браузерным тестом;
- пакетное удаление при запрещённой области отвечало «200» с ошибками по элементам вместо отказа (файлы при этом не удалялись);
- запись `jwtSecret` шла в общий файл вместо переданного (затрагивала только тесты);
- в версии без проверки доступа к «локальному» серверу пользователь, которому разрешён только удалённый сервер, получил бы доступ к основному (как и в 1.5.0 это проверялось по списку серверов — проверка восстановлена).

## 4. Скорость (модель «до» воспроизведена по коду 1.5.0)

`node tools/benchmark.js 1024` — файл 1 ГБ, 1 ядро, Node 22, диск песочницы:

| Операция | Время | Макс. «заморозка» панели |
|---|---|---|
| ДО: `copyFileSync` | 2,27 с | **2263 мс** |
| ДО: поток с буфером 64 КБ | 2,37 с | 8 мс |
| ПОСЛЕ: `pipeline`, буфер 4 МБ, прогресс | 2,07 с | 6 мс |
| Список 20 000 файлов, ДО (`statSync` по всем) | 0,09 с | 78 мс |
| Список 20 000 файлов, ПОСЛЕ (страница 500) | 0,05 с | 24 мс |
| Список 20 000 файлов, ПОСЛЕ (сортировка по размеру) | 0,28 с | 21 мс |

Главный выигрыш — не пропускная способность, а то, что панель не замирает, и что операции стали управляемыми (отмена, прогресс, докачка). Разница между буферами 64 КБ и 4 МБ в повторных запусках колебалась в пределах 0–25%, поэтому **ускорением в разы заявлять нельзя**. Сам `copyFileSync` на одном диске был не медленнее; его недостаток — блокировка.

Большой файл через сервер (localhost, песочница, 1 ядро, два прогона): 1,5 ГБ загружено частями по 16 МБ за 7,6–10,5 с (≈150–200 МБ/с) и скачано за ≈3,1–3,2 с (≈480 МБ/с), хэш SHA-256 совпал; потребление памяти процессом выросло на ≈30–35 МБ. Сетевых задержек в этом измерении нет.

## 5. Тесты

`npm test` — 100 проверок. В последнем прогоне все прошли (на заглушках пакетов, см. ниже).

Покрыто: таблица прав и покрытие каждого маршрута правилом; защита путей (`../`, абсолютные, символьные ссылки, секреты); загрузка (части, обрыв посреди части, остановка передачи, докачка, неверное смещение, чужая загрузка, лимиты, нехватка места, 500 ГБ через подставное свободное место, очистка); скачивание (Range, If-Range, HEAD, 416, кириллица, билеты, ZIP, защита); файловые операции; пакетное удаление; копирование/перемещение/отмена; распаковка tar.gz; жизненный цикл приложений; «Использовать проект» от анализа до созданного приложения; задачи; WebSocket и право «Просмотр логов»; права через API (роли, индивидуальные права, обход через `disk`, повышение привилегий, пароль, подбор); удалённый сервер через прокси (файлы, загрузка, докачка, скачивание, права на панели и агенте); обновление со старой базы; файл 1,5 ГБ; интерфейс в Chromium (вход, «назад/вперёд», загрузка файлов и папок, выделение, меню, переименование, поиск, сортировка, удаление, копирование, «Использовать проект», скрытие кнопок по правам, редактор прав, **отсутствие ошибок JavaScript в консоли**).

### Что НЕ проверено — и почему (проверьте у себя)

1. **Настоящие npm-пакеты.** В среде разработки не было сети, поэтому `express`, `better-sqlite3`, `bcryptjs`, `jsonwebtoken`, `archiver`, `unzipper`, `node-cron`, `pidusage` заменены в тестах простыми заглушками (`test/shims`, в работу панели не входят). Логика панели проверена, но поведение настоящих пакетов — нет. После `npm install` тесты **сами переключаются на настоящие пакеты**: запустите `npm test` у себя — это главная проверка, которую нужно сделать после установки.
2. Резервные копии и их восстановление (используют `archiver`/`unzipper`), распаковка ZIP/RAR/7z — в тестах не выполнялись; перенесённый код изменён минимально (пути проходят через новый модуль защиты).
3. Windows (пути, `taskkill`, службы), systemd, Docker, HTTPS и nginx.
4. Физические боковые кнопки мыши — проверена история браузера (`goBack/goForward`, которые использует и сам браузер для этих кнопок), но не нажатие железных кнопок.
5. Потоковое сохранение файла через системное окно «Сохранить как» (File System Access API): вызывает диалог ОС, который автоматизированно не проверяется; запасной путь (обычное скачивание браузером) проверен.
6. Реальные 500 ГБ и большие файлы через сеть и nginx — проверено 1,5 ГБ по localhost; предел 500 ГБ проверен на уровне логики сессии.
7. Раздел «Docker», «Система/оборудование» — запросы отвечают (smoke-проверка), содержательно не тестировались.

## 6. Оставшиеся ограничения и задачи

- Токены удалённых серверов хранятся в `server.db` открытым текстом (панели они нужны для подключения). Защитите папку панели; шифрование потребует отдельного хранилища секретов.
- Права `apps.create`, `apps.edit`, консоль, `files.edit`/`upload`/`extract`, `backups.restore`, Docker и задачи фактически равны выполнению кода на сервере. Это свойство самой панели; в интерфейсе такие права помечены ⚠.
- Копирование между разными удалёнными серверами не поддерживается (только в пределах одного).
- Целостность загрузки проверяется по размеру и TCP/TLS; побайтовая контрольная сумма не считается (это замедлило бы передачу).
- `lib/requirements.js` (проверка требований проекта) не подключён ни к одному маршруту: оставлен без изменений как заготовка.
- Страницы «Задачи», «Backup», «Система», «Runtime», «Docker» перенесены из прежнего кода с автоматическим форматированием, но не переписаны построчно: в них остаются короткие имена переменных. В файлах `lib/processes.js`, `lib/backups.js`, `lib/tasks.js`, `lib/app-config.js`, `lib/hardware.js`, `lib/archive.js`, `lib/launcher.js` комментарии есть, но дальнейшее переименование переменных — отдельная работа.
- Политика защиты браузера допускает встроенные скрипты (`unsafe-inline`), так как перенесённые страницы используют обработчики `onclick="…"`.
- Переносимые страницы всё ещё используют окна `alert/confirm` в части сценариев.
- Нужно вручную: настройки прокси (раздел 4 README), HTTPS, запуск от отдельного пользователя, смена пароля `admin`.
